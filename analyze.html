Key Takeaway: Vyper Guard has unique strengths in Vyper specialization, on-chain analysis, and runtime monitoring — but its core static analysis engine (regex-based) is fundamentally weaker than tools that use proper IRs, CFGs, and data-flow graphs. This is the most critical gap to close.
🔬 Implementation Gap Analysis
Every wrong or missing implementation in Vyper Guard vs industry standards
CRITICAL No Intermediate Representation (IR)

Slither converts source → SlithIR (SSA form) before running detectors. This enables precise dataflow, taint tracking, and alias analysis. Vyper Guard operates purely on raw source text with regex patterns. This fundamental gap means:

  • Cannot track a value through multiple assignments
  • Cannot determine if two variables alias the same storage slot
  • Cannot follow tainted user input through internal function calls
  • All "dataflow" is approximated by looking at preceding lines in regex

Fix: Build a lightweight VyperIR layer that converts parsed AST into SSA-like form with def-use chains. Can start with a simplified version covering the most common patterns.

CRITICAL No Control Flow Graph (CFG)

Without a CFG, the CEI detector and reentrancy detector cannot determine all paths through a function. They currently scan line-by-line in order. This causes:

  • False positives: CEI flagged when code is inside an unreachable branch
  • False negatives: CEI missed when violation is in a conditional branch
  • Cannot detect dead code (unreachable code after always-reverting checks)
  • Loop analysis is approximated via indentation heuristics

Fix: Build a basic CFG from the parsed AST. Track basic blocks, branch conditions (if/elif/else, for loops). Use it to upgrade loop detection and CEI analysis.

CRITICAL Severely Limited Detector Count (12 vs 80-100+)

Vyper Guard has 12 detectors. Slither has 80+, Aderyn has 100+. Missing critical categories:

  • Flash loan attacks
  • Price oracle manipulation
  • Frontrunning vulnerabilities
  • Signature replay attacks
  • Unsafe ERC-20 interactions (missing safeTransfer)
  • Incorrect use of .transfer() vs .send()
  • Uninitialized storage variables
  • Missing zero-address validation
  • Incorrect modifier usage
  • tx.origin authentication
  • Weak randomness sources
  • Missing return value checks on ERC-20 transfer
  • Locked ether (receive funds, no withdraw)
  • Block gas limit DoS
  • Storage collision in proxies
  • Shadowed state variables
HIGH "AI Triage" is Not AI — It's Hardcoded Sorting

The ai_triage.py module is labeled as "AI-assisted triage" but contains:

# This is NOT AI. This is hardcoded severity ranking: def _confidence(severity, evidence_count): base = { Severity.CRITICAL: 0.92, # hardcoded Severity.HIGH: 0.86, # hardcoded ... }[severity] # returns the hardcoded value + tiny bonus for evidence count

The README says "AI advisory triage support" — this is misleading marketing. Real AI triage would call an LLM to provide context-aware reasoning about each finding, not return a lookup table. Either actually integrate an LLM (optional, with clear opt-in), or rename this to "Priority Triage" / "Deterministic Triage" and update all docs to be accurate.

HIGH Custom Line-by-Line Parser vs Real Compiler AST

The ast_parser.py is a 382-line hand-written regex parser. Known limitations documented in the file itself:

# From ast_parser.py docstring: # Limitations (by design): # - Multi-line expressions that span 3+ lines may not be fully captured. # - Complex constant expressions are stored as raw strings. # - This is NOT a replacement for a full compiler AST

Slither and Aderyn use actual compiler AST output. Vyper provides vyper --ast which outputs proper AST JSON. The tool already has semantic_mode=compiler but it's optional and the fallback (regex) is default. The compiler AST path should be the primary analysis mode, not an opt-in extra.

HIGH CEI Detector Has Architectural False Positive Issue

The CEI (Checks-Effects-Interactions) detector is purely line-order based:

# Current: checks if ANY state write exists AFTER external call # In the raw source line order. This causes FPs: def safe_function(): # check assert condition # interaction (external call in true branch) if should_call: raw_call(addr, b"") # effect (state write AFTER the if block) self.counter += 1 # ← FALSELY FLAGGED as CEI violation

In reality, self.counter only executes after the call completes — this is safe. A proper CFG-based analysis would see that the state write dominates only AFTER the external call, and with @nonreentrant, this is acceptable. Without a CFG, the detector makes conservative (wrong) assumptions.

HIGH Reentrancy Detector Missing Cross-Function Analysis

The reentrancy detector (MissingNonreentrantDetector) does check if a function without @nonreentrant has state writes AND the contract has other external-call functions. However, it cannot detect which specific cross-function reentrancy paths are dangerous — it just checks "any other function in this contract makes external calls." This produces both false positives (detected when paths don't actually lead there) and false negatives (misses complex call chains).

Slither's approach: Builds the actual call graph and identifies specific paths where function A calls external contract, which re-enters function B that reads stale state written by function A.

MEDIUM No Code Complexity Metrics (Cyclomatic Complexity, etc.)

Solidity-by-Metrics computes cyclomatic complexity, SLOC, risk profiles, and capability flags. Vyper Guard's stats command produces basic line counts and function lists but no complexity metrics. Audit firms use complexity metrics to:

  • Estimate audit duration and cost
  • Identify high-risk functions needing deeper review
  • Track code quality trends over releases
  • Prioritize which functions to manually review

Fix: Implement cyclomatic complexity (count branches: if/elif/for/while/and/or) per function, maintainability index, and assembly/low-level call flags in the stats command.

MEDIUM No Plugin / Custom Detector API

Slither, Aderyn, and Mythril all have public APIs for writing custom detectors. This enables:

  • Audit firms to write protocol-specific detectors for each engagement
  • Community contributions without PRs to the main repo
  • Users to disable specific detectors causing FPs for their codebase

Vyper Guard's BaseDetector class is internal but not exposed as a public plugin API. The --disable-detectors flag exists but there's no way to add new detectors without modifying the source.

LOW Security Score is Simplistic / Not Calibrated

The scoring formula (base 100, subtract fixed amounts per severity) is not calibrated against real-world data. Issues:

  • A contract with 1 CRITICAL gets the same base penalty as one with 3 MEDIUM — both might score identically
  • No weight for confidence level (HIGH confidence finding = same penalty as LOW confidence finding)
  • No normalization by contract size (1 finding in 100-line contract vs 10000-line contract)
  • The tier caps prevent score from reaching 0 even for severely broken contracts
GOOD Runtime Monitoring — Unique Competitive Advantage

No other tool in this comparison has built-in on-chain transaction monitoring with alerting. This is a genuine competitive differentiator. The alerting system (webhook, email, Slack) combined with the baseline + anomaly detection creates a unique offering. However, the current implementation needs to be made more robust:

  • Pattern matcher needs more sophisticated rules (MEV patterns, sandwich attacks)
  • Should add integration with Tenderly/Forta for production use
  • Should support EVM trace analysis, not just transaction-level monitoring
